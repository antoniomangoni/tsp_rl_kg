# Meta-Spec: Guidelines for AI Agent Specifications (Python & uv Edition)

## Objective

To define the structure and behavior for AI agent specifications. An effective spec must act as a single, unified source of truth that dictates the *why* (goals), the *what* (architecture), and the *how* (execution steps).

Create a spec and save it in `docs/specs`.

## 1. Core Structure of a Spec

Every technical specification generated by the agent must include the following sections:

* **Goals & Non-Goals:** Explicitly define what success looks like and what the agent should *not* attempt to do (e.g., "Non-Goal: Preserving backwards compatibility with Python 3.10").
* **Technical Decisions & Stack:** Clear definitions of the tools, package managers, and architectural rules (e.g., `uv` for dependency management, Python 3.13+, `pyproject.toml` as the single source of truth).
* **Project Structure & Git Workflow:** Define directory layouts (e.g., `src/` for application code, `tests/` for `pytest` suites) and version control rules (e.g., branch naming, commit message formats, PR requirements).
* **Testing & Conformance:** Specify testing frameworks (e.g., `pytest`), locations of test files, coverage expectations, and language-independent conformance criteria.
* **Sequence & Workstreams:** A numbered, chronological list of execution phases so the agent knows exactly what order to tackle the problem in.
* **Target Files:** A concrete list of the specific files or directories expected to change. This restricts the agent's search space and prevents scope creep.
* **Commands & Code Style:** Concrete examples of executable commands (e.g., `uv sync`, `uv run pytest -v`, `uv run ruff check`) and stylistic preferences (e.g., strict type hinting, docstring formats).
* **Extended TOC (For Large Specs):** If the spec covers extensive ground, generate a hierarchical Table of Contents condensing each section into 1-2 sentence summaries with reference tags to serve as a low-token mental map for the agent.

## 2. Boundaries & Acceptance

Every spec must define strict operational boundaries and verification methods:

* **The Three-Tier Actions:**
  * **Always Do:** Actions the agent must perform automatically (e.g., "Always run `uv run pytest` before proposing a commit").
  * **Ask First:** High-impact actions requiring human approval (e.g., "Ask before modifying database schemas or adding new dependencies to `pyproject.toml`").
  * **Never Do:** Hard stops (e.g., "Never commit secrets," "Never manually edit files inside `.venv/` or `__pycache__/`," "Never use `pip install` directly").
* **Rejection Criteria:** Explicit conditions under which a task or workstream is considered failed or incomplete (e.g., "Migration is incomplete if any `requirements.txt` files remain").
* **Self-Auditing:** Instructions for the agent to cross-reference its output against the Goals, Non-Goals, and Rejection Criteria after completing each sequence step.

## 3. Agent Execution Workflow

To avoid context overload and "house of cards" code, agents must interact with the spec using these rules:

* **Plan-First Execution:** Always analyze the codebase in read-only mode to draft and refine the specification *before* generating or modifying any actual code.
* **Persona Adherence:** Adopt the specific role required for the task (e.g., `@docs-agent` for technical writing, `@test-agent` for QA) and adhere strictly to that domain's tone and boundaries.
* **One-Task Focus:** When implementing, focus only on the current step in the "Sequence" and pull in only the specific context or "Target Files" needed for that exact sub-problem.
* **Iterative Evolution:** The spec is a living document. If a requirement changes, an edge case is discovered, or a test fails, the agent must update the spec document *first* before modifying the codebase.
